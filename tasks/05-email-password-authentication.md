# Task 05 — Email and password authentication

## Context and dependencies
Tasks 02 and 04 provide the app shell and secured local backend. Task 02a provides the early Android shell for device verification. The first release has private per-user courses, email/password sign-in, verification, and password reset. Local email tests do not depend on hosted accounts or SMTP; Task 00b records those release prerequisites.

## Work
Configure the Supabase client with URL and publishable key from environment variables. Implement registration, in-app email code entry and verification, sign-in, sign-out, password-reset request, recovery-code entry, password update, session restoration, and protected routes. Configure local Auth templates to email the Token value; use Supabase verifyOtp with the appropriate confirmation/recovery type. This single flow must work in web and Android without mobile deep links. Show clear states for unverified email, invalid credentials, expired code, resend throttling, and network failure. Keep local redirect URLs for any unavoidable Auth links and document production URL changes for Task 27. On sign-out, clear auth-dependent in-memory state and invoke the offline cache cleanup hook that Task 24 will implement. Do not persist passwords in application storage. [Supabase templates](https://supabase.com/docs/guides/auth/auth-email-templates), [verifyOtp](https://supabase.com/docs/reference/javascript/auth-verifyotp).

Define separate states for online authenticated access, offline access to this device's previously authorized downloads, and signed-out/reauthentication-required access. After a successful online sign-in, retain a device-local owner binding for offline content. On Android, an expired access token or transient refresh/network failure must not erase that binding or block cached reading after restart. This binding is not a backend credential: offline routes permit only already-downloaded reading and queued progress for that owner, never authoring, tests, reviews, new downloads, or remote requests without valid authentication. Keep Supabase session credentials separate from chapter caches. On reconnect, refresh/validate the session and match its user ID before syncing. A definitive invalid/revoked session locks cached access and requires online sign-in to the same account; preserve pending data for that recovery, but never expose it to another account. Revocation cannot be detected while disconnected; document this offline limitation. Explicit sign-out locks access immediately and initiates durable cleanup even without connectivity, with the Task 24 cleanup hook blocking any subsequent account switch until completed.

## Verification
Use local Supabase Auth and its mail testing facility to create a user, enter the confirmation code, sign in, reload, enter a password-recovery code, update the password, and sign out. Run this flow in the website and the Task 02a Android shell using its development-only local-backend configuration. Test invalid/expired codes and resend limits. Test direct loading of protected routes while signed out and the distinction between token expiry, transient refresh failure, and definitive session rejection. Verify offline route guards with a seeded owner/cache fixture now, then repeat with real downloads in Tasks 23–24. Verify the auth UI follows Task 01 mockups and works by keyboard.

## Done when
A verified user can enter and leave protected screens on web and Android. Signed-out users cannot access private data, and offline reading has an explicit owner-bound access contract independent of online token freshness.
